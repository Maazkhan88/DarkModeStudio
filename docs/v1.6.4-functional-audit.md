## 1. Database Upgrades & Schema Lineage

- **Historical v4 Schema**: Preserved as immutable artifact in `app/schemas/com.darkmodestudio.commandcenter.core.database.DmsDatabase/4.json` (identity hash `81b343b1d29f50ae51d109db735fd323`).
- **Current v5 Schema**: Bumped `@Database(version = 5)` and exported `5.json` (identity hash `a00c511a492ec6dfe365e990325a57e6`).
- **Migration Path 4 $\rightarrow$ 5**:
  - Adds `repositoryDefaultBranch` column to `projects`.
  - Creates composite index `index_tasks_projectId_status` on `tasks(projectId, status)`.
  - Drops redundant single-column index `index_tasks_projectId`.
  - Migrates `repository_file_entries` to branch-scoped schema with index on `(repositoryFullName, branch, path)`.
- **Validation**: Verified using `androidx.room.testing.MigrationTestHelper` in `RoomMigrationTest.kt`. Data across all entities is verified intact post-migration.

## 2. GitHub Sync & Project Relational Preservation

- **Non-Destructive Parent Updates**: `ProjectDao` separates `@Insert(onConflict = ABORT)` from `@Update`. For existing projects, `GitHubSyncer` issues an in-place `updateProject()`, avoiding SQLite `REPLACE` that triggers `ForeignKey.CASCADE` deletes on child tables.
- **Child Entity Protection**: User-created milestones (`project_milestones`), blockers (`project_blockers`), local activities (`project_activities`), and tasks (`tasks`) remain fully preserved across sync cycles.
- **Truthful Imported Status**: Newly discovered GitHub repositories are assigned `ProjectStatus.IMPORTED` (`"Imported"`, hollow node style) with `0f` phase weights and empty milestones.
- **Planning Metadata Ownership**: Synchronizing an existing repository updates only GitHub-owned telemetry (`repositoryFullName`, `repositoryDefaultBranch`, `owner`, `createdAt`, `lastUpdate`, `description`) while retaining user-defined status, due dates, milestones, task progress, and phase weights.
- **Validation**: Verified in `GitHubProjectPreservationTest.kt`.

## 3. Crash-Safe Legacy Database Fileset Migration

- **Atomic Staging Architecture**: Staged via temporary files (`.migrating`) in `DmsDatabase.migrateLegacyDatabaseFileIfPresent()`.
- **Promotion Sequence**:
  1. Staging companions (`tempWal -> currentWal`, `tempShm -> currentShm`) promoted first.
  2. Temporary primary DB (`tempDb -> currentDb`) promoted **last**, serving as the atomic commit point.
- **Process Crash Recovery**: If the application crashes before the primary DB is promoted, no partial database is visible to Room. On the next startup, stale temporary files are cleaned up and migration safely retries from the intact legacy source.
- **Source Deletion Safeguard**: Legacy source files are deleted only after the final promoted fileset is verified.
- **Validation**: Verified in `LegacyDatabaseMigrationTest.kt` across 7 test scenarios, including simulated pre-promotion crashes, stale temp file cleanup, and real SQLite WAL mode transactions.

## 4. Repository Files Cache & Branch Scoping

- **Cache Keys**: Format is `${repositoryFullName}:${branch}:${path}:${name}`.
- **DAO Queries**: Scope all selections and deletions by `(repositoryFullName, branch, path)`.
- **Branch Coexistence**: Validated in `RepositoryFilesRepositoryTest.kt` that cache entries for `main` and `develop` branches coexist without cross-branch contamination.
- **Unlinked State**: Projects without a linked GitHub repository correctly report `RepositoryFilesState.NotLinked` with clear action prompts in UI.
